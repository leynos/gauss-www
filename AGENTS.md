# Contributor guide

This repository contains the Gauss design brief and an import-ready framework
for the Gauss subsite of `df12-www`.

- `config/gauss.yaml`, `templates/gauss/`, `src/styles/gauss.css`, and
  `src/static/gauss/` form the portable subsite framework.
- `references/` holds design evidence and direction. It is not generated site
  output.
- `.build/` and `.preview/` are disposable output and must remain untracked.

The framework will ultimately live in `../df12-www`. Read that repository's
`AGENTS.md` before significant integration work; it remains authoritative for
the current generator and deployment pipeline.

## The subsite is generated

The published site is static output generated by the `df12_pages` Python
application. Never hand-author or track generated HTML.

- `config/gauss.yaml` contains the `gauss:` mapping merged beneath `sites:` in
  `df12-www/config/pages.yaml`.
- `templates/gauss/` owns page structure and copy.
- `src/styles/gauss.css` is the ahead-of-time Tailwind CSS entrypoint.
- `src/static/gauss/assets/` owns assets copied into `/gauss/assets/`.
- Shared legal prose remains owned by `df12-www/config/shared/` and renders
  through Gauss chrome.

Change source configuration, templates, styles, or static assets, then rebuild.
Never edit `.preview/`, `public/`, or compiled CSS by hand.

## Preserve the import boundary

| This repository | Destination in `df12-www` |
| --- | --- |
| `config/gauss.yaml` | `config/pages.yaml` beneath `sites:` |
| `templates/gauss/` | `templates/gauss/` |
| `src/styles/gauss.css` | `src/styles/gauss.css` |
| `src/static/gauss/` | `src/static/gauss/` |

The parent build must compile `src/styles/gauss.css` to
`public/gauss/assets/tailwind.css`. Do not import `.build/`; it exists only for
the isolated local preview.

Do not introduce another page generator, frontend framework, browser-side
Tailwind compiler, runtime content service, or asset pipeline. Use the parent
`df12_pages` interfaces and static-copy contract. Capabilities missing from the
parent are architectural changes to `df12-www`, not reasons to fork it here.

`make preview` must compose temporary configuration and must not modify the
sibling checkout. `make dev` installs locked Bun dependencies here and locked
uv development dependencies in `../df12-www`, then runs the same
`concurrently`/`chokidar-cli`/`http-server` loop as the parent.

## Tailwind and daisyUI are the style abstraction

Ahead-of-time compiled Tailwind CSS v4 and daisyUI v5 are the core style
abstraction. The local guides are authoritative:

- [daisyUI v5 guide](docs/daisyui-v5-guide.md)
- [Tailwind CSS v4 guide](docs/tailwind-v4-guide.md)
- [Semantic Tailwind with daisyUI](docs/semantic-tailwind-with-daisyui-best-practice.md)

Use `../df12-www/src/styles/mxd.css` and the `mxd` templates as the worked
example for a dedicated subsite entrypoint, explicit `@source` discovery, a
custom daisyUI theme, and parent build integration. Follow the modern layers,
not mxd's historical long utility strings or third-party font requests.

Apply the style system in this order:

1. semantic HTML and native controls;
2. daisyUI components and theme roles where they fit;
3. Tailwind utilities for local layout, responsive behaviour, and state;
4. Gauss semantic classes for repeated product concepts and page structures.

Templates should say what an element is: `gauss-port`, `gauss-specimen`,
`gauss-command-map`. Avoid opaque colour literals, appearance-named classes,
and repeated utility soup. Define primitive values in `@theme`, map semantic
roles through the daisyUI theme, and implement repeated wrappers with
`@utility` or narrowly scoped `@apply` using Tailwind utilities only.

Never `@apply` daisyUI component classes such as `btn` or `card`. Compose those
classes in markup. Keep selector specificity low and let local utilities win.
Do not add `tailwind.config.js`; Tailwind v4 configuration is CSS-first.

Use semantic colour roles such as `primary`, `base-100`, and `success` rather
than literal palette utilities. Every `*-content` pairing must meet its contrast
requirement. Keep required assets self-hosted; the published subsite must not
depend on third-party browser requests.

## Gauss visual boundaries

Gauss is a vector illustration tool, not CAD, desktop publishing, or print
production software.

- Keep deconstructed paths, Bézier handles, nodes, and alignment guides.
- Use a clean white or cool near-white canvas.
- Avoid unbleached backgrounds, graph-paper rules, crop marks, registration
  systems, dimensions, and architectural notation.
- Use technical marks only when they describe a vector object or interaction.
- Keep the current arched-curve logo proposal compact. The botanical specimen,
  not the logo, is the expressive hero.

Treat `references/design-sample.png` as a hierarchy and interaction reference,
not a pixel specification or evidence that every labelled capability ships.
Verify all `SHIPPED`, `PARTIAL`, and `PLANNED` claims against current Gauss code.

## Content and templates

- Keep routes, navigation, status records, and repeated facts in structured
  configuration or shared template data.
- Render repeated structures with Jinja loops and macros.
- Keep route templates thin when a shared page shape fits.
- Distinguish implemented, partial, and planned capabilities.
- Use British English with Oxford spelling in maintained prose.
- Keep maintained source files around 400 lines; split by responsibility before
  a file becomes difficult to review.

Reach for the cheapest capable layer: build-time data and Jinja first, semantic
HTML and CSS second, and optional JavaScript only when CSS and native platform
features cannot provide the behaviour. Load scripts with `defer`, scope them
through `data-*` attributes, and preserve complete content without JavaScript.

## Accessibility and responsiveness

The subsite must meet WCAG 2.2 AA and remain at zero automated accessibility
violations.

- Use landmarks, one clear page heading, ordered heading levels, and
  descriptive link text.
- Provide a keyboard-visible skip link and the Gauss offset double-rule
  `:focus-visible` treatment.
- Keep targets at least 24 by 24 CSS pixels; target 44 by 44 for primary touch
  controls.
- Meet 4.5:1 contrast for body text and 3:1 for large text and non-text UI.
- Do not communicate state through colour alone.
- Respect `prefers-reduced-motion` and forced-colour modes.
- Test narrow and wide viewports. Horizontal page overflow is a defect.

Automated audits do not replace visual, keyboard, or screen-reader inspection.

## Validation

Use Makefile targets and run gates sequentially:

```bash
make check
make preview
```

Use `make dev` for interactive work. It performs locked dependency
synchronization, an initial build, continuous rebuilds, and serves `.preview/`
on `DF12_PORT` (8080 by default).

For renderer changes, also run:

```bash
uv run --project ../df12-www ruff format --check scripts/render-framework.py scripts/validate_site.py
uv run --project ../df12-www ruff check scripts/render-framework.py scripts/validate_site.py
uv run --project ../df12-www ty check scripts/render-framework.py scripts/validate_site.py
```

After rendering, verify routes and internal links, inspect the homepage and a
nested route in a real browser, test narrow and wide viewports, check the
keyboard path, and run an axe-core WCAG 2.2 AA audit.

## Documentation

Keep [the import guide](docs/importing-into-df12-www.md) aligned with the source
mapping and parent build procedure. Update the design brief when implementation
decisions settle open questions rather than allowing the two to drift.

Run `make markdownlint` and `make nixie` for prose changes.

## Commit messages

Write an imperative summary under 72 characters, with no conventional-commit
prefix or trailing full stop. Explain what changed and why in a wrapped body
when useful. Do not add generated-tool attribution trailers.
